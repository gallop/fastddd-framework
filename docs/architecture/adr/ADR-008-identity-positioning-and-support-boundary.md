## 1. 背景（现状，代码级证据）

- **四层 AI 消费栈现状**（W7 规划 §1）：③ sources/javadoc jar 真值已随制品轮交付（21 坐标、sources/javadoc 各 18）；①skill 导航（缺）、②生成式契约摘要（缺）、④契约套件验收（缺）。宿主/AI 消费者当前只能读 sources jar 原文，无结构化契约面与自实现验收通道。
- **治理宣示缺口**：identity 的引擎定位、PG 参考平台边界、保留表名与 schema 所有权、自实现支持边界此前散落在 W 系列设计稿与执行记录中，无一处权威宣示——外部消费者不可见、不可引用。
- **交付事实**：`io.github.gallop.fastddd:*:1.1.0-M2` 21 坐标含 identity 四模块（core 纯 Java 端口/用例、reference-pg、spring-boot-starter、feishu）；`V1–V4 + optional` 迁移随 reference-pg 制品交付；四张通用名表裸建宿主默认 schema（V1 实文）。

## 2. 决策（D-1…D-6 拍板值；每项与备选落选理由成对在册）

### 2.1 D-1：identity 定位 = engine 型可选子系统

**决策**：engine 型可选子系统（可选依赖、宿主内嵌、随宿主进程运行），非独立服务、非纯函数库。判定依据三层判别式：

1. **状态本征**——主体/绑定/会话/目录镜像是有生命周期的状态（authEpoch、代次、租约、撤销门禁），非无状态工具面；
2. **难度沉淀在存储协议**——advisory 锁键级序列化（W5 R2-P1-1 处置）、开放代唯一索引互斥、发布单事务原子切换、H_before/H_after 水位合并，难度在 PG 协议层而非业务编排层；
3. **同库同事务硬约束**——统一签发/审计与业务变更同库同事务是 v0.2 需求（§8 统一签发事务、T2/T4 事务责任表）推动的硬约束。

**备选落选：独立身份服务**——统一签发/审计同库同事务是需求推动的硬约束，服务化把单机事务退化为分布式事务，牺牲一致性换取部署形态，与需求方向相反（详见 2.6 逃生门）。

**备选落选：只发端口不发实现（纯接口库）**——失去参考平台行为责任：难度沉淀在存储协议（判别式 2）意味着不提供 reference-pg 实现就无法对「可用性」承担任何责任，自实现宿主各自重造 advisory 锁/代次切换且无验收基准。

### 2.2 D-2：可移植性 = PG 参考平台、跨库非目标

**决策**：reference-pg 为唯一参考平台；跨数据库（MySQL/Oracle 等）为**非目标**，重开需 ADR 变更（§7）。存储协议（判别式 2）与 PG 特性深度耦合：`pg_advisory_xact_lock` 双参键级序列化、部分唯一索引（开放代互斥）、`ON CONFLICT` 幂等 upsert——方言适配 = 协议层重设计而非 SQL 翻译。

**备选落选：多存储方言支持**——验证矩阵按方言数 ×N 放大，单一产品阶段无消费需求支撑，且与「难度沉淀在存储协议」事实冲突（每方言都是一次协议级重验证）。

### 2.3 D-3：契约保障层级 = L1 契约套件（TCK）；L2 认证不做

**决策**：契约保障走 L1——`identity-contract-kit` 契约套件（TCK 形态，W7-d 首期覆盖 IdP 适配器域），自实现者跑套件红绿自证；L2 认证体系（官方徽章/兼容目录/认证流程）**不做**。

**备选落选：L2 认证体系**——单一产品阶段过重：认证流程的治理成本（申请/审核/目录维护/版本吊销）远超当前生态规模，TCK 已足够承载「自实现可用性」的验证责任（§5 支持边界以 TCK 结果为唯一凭证）。

### 2.4 D-4：套件分期 = IdP 适配器套件先行；存储端口套件触发制

**决策**：IdP 适配器契约套件先行（W7-d，覆盖分页游标状态机/严格成功三要素/权限族 fail-fast/不判删除/凭据 fail-closed）；存储端口契约套件**触发制**（触发 = 首个真实第三方存储实现需求）。

**理由**：IdP 适配是宿主接入必然面（飞书之外的企业 IdP 接入是消费面最真实高频的自实现点）；reference-pg 免费可用使存储端口自实现当前零需求——预先建设无消费方。

### 2.5 D-5：命名空间 = 不做表前缀；PG schema 归置为触发制正解

**决策**：不做表前缀；表名碰撞/多组件共库时以 **PG schema 归置**（JDBC `currentSchema`）为正解，**触发制**（触发即升级为独立兼容分析轮，不改默认裸建形态）。

**备选落选：表前缀**（`fastddd_identity_principal` 形态）——PG schema 机制已存在，前缀次优（无法利用 schema 级权限与搜索路径隔离，且把命名面污染到所有 SQL/索引/迁移文本）；四张通用名表裸建宿主默认 schema 是既成交付事实（V1 实文，`1.1.0-M1/M2` 已冻结），前缀化 = 破坏性迁移。

### 2.6 D-6：服务化 = 不拆独立身份服务；逃生门保留

**决策**：不拆独立身份服务（落选理由同 2.1）；**逃生门保留** = identity-core（纯 Java 端口/用例，无 web 依赖）+ reference-pg 可整体打包为独立服务进程——若未来宿主普遍要求独立部署形态，走打包形态而非重构。

## 3. 保留对象清单（承载 = W0-2 §3.4，此处只挂指针）

identity 在宿主库中保留的 schema 对象全量清单（13 表 + 唯一键 5 + 普通索引 6，行号锚定 `db/identity/` 实文）与四张通用名表「裸建宿主默认 schema」标注，承载于 [W0-2 §3.4](../../identity/w0/W0-2%20端口、事务责任与最小数据字典.md)（数据字典实文面）。新增表/索引须入清单（发布 checklist 增项，W7-a 后生效）。

## 4. schema 所有权边界

- **identity 表宿主只读**（应用代码面）：宿主业务代码不得 INSERT/UPDATE/DELETE identity 表，只能经 identity 模块端口。
- **禁自建索引/触发器/直写 SQL**：直写绕过域不变量（绑定五元组唯一裁决、authEpoch 撤销门禁、代次原子切换、证据门控规则 A–E、水位合并）；自建索引未经性能验证且可能被后续迁移破坏；触发器会与 advisory 锁/事务责任表（T1–T8）产生不可见交互。
- **升级只经随制品迁移**：`V1–V4 + optional` 随 reference-pg 制品交付，接入两形态（开发态 `initialize-schema` / 生产态宿主迁移体系拷贝）按 [W4-d 迁移交付说明](../../identity/W4-d%20迁移交付说明.md)；跨版本升级只经新版本迁移脚本，无带外 DDL 通道。

## 5. 支持边界

- **框架仅对参考实现承担行为责任**：reference-pg、starter、feishu 模块的缺陷属框架责任域；文档/发布说明所载限制（FI-05、live 校准遗留等）为边界的组成部分。
- **自实现（宿主自带 IdP 适配器/DirectorySource/存储端口实现等）经契约套件验收后进入宿主责任域**：未验收的自实现不获得任何兼容性承诺。
- **「passed identity-contract-kit @ vX」为唯一受支持声明形态**（W7-d 套件落地后生效；此前自实现一律宿主责任域——套件落地前，框架文档不得赋予任何自实现「兼容 FastDDD identity」之外的背书地位）。

## 6. 诚实弱点清单

- 四张通用名表（`principal`/`local_session`/`login_state`/`external_binding`）裸建宿主默认 schema——多组件共库时表名碰撞风险真实存在；缓解 = D-5 触发制 schema 归置（ECOS 接入期为重点盯梢项，未点火）。
- 真实飞书环境验证面残留：W3-b 六条未验证项 + W3B-N1（tenant token 吊销粘性）等 live 校准项维持待验，以官方文档 + 本地桩为当前证据层。
- 单存储参考平台：非 PG 宿主当前无受支持路径（D-2 非目标），接入前需 ADR 变更重开。
- 增量通知 M2 边界：changeLogRef 追溯窗收窄前须确认宿主投递延迟上界（W5-f 交付说明义务）。
- W7-d 落地前，「自实现可用」无机械验收通道（L1 TCK 尚未存在）——本 ADR §5 的声明形态在套件交付前仅为前瞻宣示。
- L2 不做意味着 TCK 通过声明**不可与官方认证混淆**（无徽章/目录背书），文档面须持续区分。

## 7. 重开条件

- **跨库支持**：默认非目标；经 ADR 变更重开（新 ADR 替代或修订本 ADR §2.2），重开即触发存储协议层重设计评估。
- **服务化拆分**：逃生门形态（core + reference-pg 整体包服务）被证明不足时，经 ADR 变更重开 §2.6。
- **表前缀**：仅当 PG schema 归置在真实碰撞场景被证明不可行时，经 ADR 重开 §2.5。
- **L2 认证**：多产品生态形成后再议，不预设触发条件。
